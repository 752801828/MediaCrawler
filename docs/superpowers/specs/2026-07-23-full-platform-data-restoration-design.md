# 全平台完整字段恢复设计

日期：2026-07-23
状态：已确认，待实施

## 1. 背景

当前上游版本采用教学版隐私策略：公开内容和评论中的原始用户标识、头像、签名、IP 归属地等字段不再持久化，原始用户 ID 被转换为 `creator_hash`，昵称通过 `mask_nickname()` 脱敏；部分创作者资料模型和写入流程也被删除或停用。

本项目需要永久取消本地采集与存储端的这些限制，恢复抖音、小红书、快手、微博、贴吧、知乎和 B 站的平台原始字段及创作者资料。飞书同步层继续保留现有隐私过滤，不向飞书写入完整个人字段。

## 2. 已确认范围

### 2.1 平台

- 抖音
- 小红书
- 快手
- 微博
- 贴吧
- 知乎
- B 站

### 2.2 数据类型

- 作品或内容的作者字段
- 评论作者字段
- 创作者资料
- 平台接口直接返回的头像、签名、性别、IP 归属地、关注数、粉丝数和互动数等字段

### 2.3 存储端

- MySQL
- SQLite
- CSV
- JSON
- JSONL
- MongoDB
- Excel

所有受支持的存储端接收同一份规范化完整数据对象。某个平台或某种爬取入口未提供的字段写为 `NULL` 或空值，不进行身份推断。

### 2.4 不在范围内

- 不恢复已脱敏或已经写成 `NULL` 的历史数据。
- 不自动重抓现有作品或账号。
- 不向飞书同步完整个人字段。
- 不新增平台接口没有返回的身份推断、跨平台关联或外部数据补全。
- 不修改当前创作者运营、浏览器登录态和任务规划行为。

## 3. 方案选择

采用“逐平台恢复结构化字段”的方案。

以旧定制仓库中的完整字段映射为参考，在当前新版架构中逐项恢复字段、ORM 模型和存储逻辑。不得直接用旧文件覆盖新版文件，以免丢失新版接口适配、存储后端、浏览器模式和创作者运营迁移代码。

不采用仅保存原始 JSON 的方案，因为原始 JSON 不利于按用户 ID、昵称和其他业务字段查询。不采用单独用户扩展表方案，因为会增加所有存储端的关联复杂度，且与现有旧表结构不一致。

## 4. 总体架构

数据流保持为：

1. 平台客户端获取接口响应。
2. 平台提取层读取平台实际返回的内容、评论和创作者字段。
3. 平台存储映射层生成规范化完整数据字典。
4. 存储工厂将同一数据字典交给 MySQL、SQLite、CSV、JSON、JSONL、MongoDB 或 Excel 实现。
5. 本地数据库按业务主键新增或更新。
6. 如后续执行飞书同步，现有飞书过滤器在出站前移除受限字段。

运行链路不再调用 `mask_nickname()`，也不再以匿名哈希替代原始用户 ID。`creator_hash` 字段暂时保留，用作现有查询和创作者运营模块的附加兼容字段；运行链路可继续从已经完整写入的原始 ID 生成该值，但必须同时保存原始 ID。

`tools/user_hash.py` 暂时保留以兼容仓库外部引用。运行链路不得调用 `mask_nickname()`；`anonymize_user_id()` 只允许用于生成附加的 `creator_hash`，不得替代或删除原始用户 ID。

## 5. 数据模型

### 5.1 内容和评论表

各平台内容和评论表恢复旧实现曾经写入、且当前平台响应仍能提供的原始字段。字段名称沿用现有数据库的旧列名，避免产生同义重复列。

典型字段包括：

- 原始用户 ID
- 平台辅助用户 ID，例如抖音 `sec_uid`、`short_user_id`、`user_unique_id`
- 原始昵称
- 头像 URL
- 用户签名或简介
- 性别
- 用户主页 URL
- IP 归属地

现有作品 ID、评论 ID、发布时间、内容、互动数、父评论 ID、图片等业务字段保持不变。

### 5.2 创作者资料表

恢复各平台被删除或停用的创作者资料模型及写入路径：

- 抖音：`dy_creator`
- 小红书：`xhs_creator`
- 快手：对应 creator 表
- 微博：`weibo_creator`
- 贴吧：`tieba_creator`
- 知乎：`zhihu_creator`
- B 站：`bilibili_up_info` 及现有采集流程需要的相关资料表

创作者记录以平台原始用户 ID 为业务键做新增或更新。平台返回的粉丝数、关注数、作品数、互动数等使用现有字段名称和兼容类型。

现有 `dy_creator_history`、`xhs_creator_history` 等历史表不自动导入或重写；只有未来正常执行相关采集时，才按现有增量策略写入。

### 5.3 兼容字段

`creator_hash` 保留在内容和评论 ORM 中，避免破坏当前索引、查询和 `creator_ops` 读取逻辑。恢复完整字段后：

- 原始用户 ID 是本地完整数据的主要身份字段。
- `creator_hash` 可继续由同一原始 ID 生成，作为兼容和分组字段。
- 昵称写入平台返回的原始值，不再写入星号脱敏值。

## 6. 平台适配原则

每个平台单独实现字段映射，兼容同一平台可能存在的不同响应结构。例如快手评论同时兼容 snake_case 和 camelCase，抖音头像按多个候选尺寸依次回退。

字段获取遵循以下规则：

- 只读取接口响应直接提供的值。
- 缺少可选字段时写空值，不使整条记录失败。
- ID 在存储前规范化为字符串。
- 数量和时间字段沿用当前 ORM 可接受的类型。
- 嵌套字典和列表在访问前进行空值保护。
- 不把整份原始接口响应写入日志。

## 7. 数据库升级

SQLAlchemy `create_all()` 不会为已存在的表自动增加新 ORM 列，因此需要显式、幂等的结构升级。

升级器执行以下操作：

- 检查当前数据库类型。
- 读取现有表和列。
- 只创建缺失的 creator 表。
- 只增加缺失的原始字段和必要索引。
- 不删除列、表、索引或数据。
- 不修改现有记录。
- 重复执行得到相同结果。
- 任一结构变更失败时停止后续真实抓取，并输出表名和字段名，不继续进行部分写入。

SQLite 使用其兼容的结构变更方式；MySQL 使用明确的 `ALTER TABLE ... ADD COLUMN`。新建数据库直接由完整 ORM 创建全部表。

## 8. 各存储端一致性

平台映射层负责生成完整数据字典，存储后端不得再次删除或脱敏字段。

- MySQL/SQLite：ORM 模型包含完整字段并执行按业务键 upsert。
- CSV/JSON/JSONL：输出完整数据字典中的全部键。
- MongoDB：保存完整数据字典，以作品 ID、评论 ID或用户 ID 更新。
- Excel：表头包含完整字段；现有文件缺少新表头时按当前 Excel 存储策略安全扩展或生成新输出。

不要求不同平台拥有完全相同的字段集合，只要求同一平台的一条规范化记录在各存储端保持一致。

## 9. 飞书边界

飞书同步保持当前隐私边界：

- `creator_ops.sync.sanitize_comment_fields()` 继续删除个人字段。
- 飞书 schema 中的限制字段集合保持不变。
- 本地 MySQL 中的完整字段不得绕过过滤器进入飞书 payload。
- 新测试必须同时证明本地完整写入和飞书受限输出。

## 10. 错误处理和日志

- 平台缺少可选字段时仅保留空值。
- 缺少作品 ID、评论 ID或创作者用户 ID 等业务主键时跳过该记录并记录结构化警告。
- 单条记录的字段解析问题不得使其他已取得记录丢失。
- 数据库结构不兼容时在抓取前失败，不在写入中途自动删表或重建表。
- 日志记录平台、任务、作品 ID、评论 ID和错误类型，不额外打印完整用户资料。
- 存储失败保留原始异常类型，便于定位列名或类型问题。

## 11. 测试策略

### 11.1 单元测试

替换当前用于强制脱敏的 `no_user_info` 测试，新增完整字段测试：

- 抖音内容、评论和创作者
- 小红书内容、评论和创作者
- 快手内容、两种评论响应和创作者
- 微博内容、评论和创作者
- 贴吧内容、评论和创作者
- 知乎内容、评论和创作者
- B 站视频、评论、动态和 UP 主资料

每个测试验证原始 ID、昵称及平台可提供的其他资料与输入 fixture 一致。

### 11.2 ORM 和存储测试

- 使用 SQLite 临时库验证完整 ORM 构造和写入。
- 验证内容、评论和 creator 的新增与更新。
- 验证 CSV、JSON、JSONL、MongoDB 和 Excel 接收完整字段。
- 验证缺失可选字段不抛异常。
- 验证重复记录不会产生非预期重复行。

### 11.3 数据库升级测试

- 空数据库创建完整表结构。
- 教学版数据库升级到完整结构。
- 已包含旧列的数据库重复运行升级。
- 升级不改变现有行数和原值。

### 11.4 飞书测试

- 本地记录包含完整个人字段。
- 飞书 payload 仍不包含用户 ID、头像、签名、IP 等限制字段。

### 11.5 真实验收

完成自动化测试后，只用一个抖音作品执行评论抓取：

- 确认作品和评论成功写入。
- 确认原始昵称不再脱敏。
- 确认接口返回的用户 ID、头像、签名和 IP 等字段按实际响应落库。
- 确认未触发小红书、创作者后台或飞书同步。

## 12. 上线与回滚

上线顺序：

1. 运行自动化测试。
2. 对目标数据库执行只增不删的幂等升级。
3. 运行单作品抖音真实验收。
4. 核对数据库字段。
5. 提交并仅推送到 `752801828/MediaCrawler` 的当前 Fork 分支。

现有脱敏记录保持不变，新逻辑只影响未来采集。

如需回滚代码，可恢复到实施前提交。数据库新增列和表可保留为空，不需要删除；旧代码会忽略它们。此方式避免破坏已写入的新旧数据。

## 13. 完成标准

- 7 个平台的运行链路不再调用昵称脱敏或仅哈希身份替代逻辑。
- 平台实际返回的完整用户字段能进入所有本地存储后端。
- 创作者资料表和写入流程恢复。
- 数据库升级无删除操作且可重复运行。
- 已有脱敏数据不被修改，也不自动重抓。
- 飞书继续过滤个人字段。
- 自动化测试通过。
- 单作品抖音真实抓取验证通过。
